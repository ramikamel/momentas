# momentas Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Native execution in the current chat is the recommended default for this tightly connected, time-limited MVP; the user authorized implementation on 2026-10-24.

**Goal:** Let someone create and refine an visualized memory, share the approved version, and exchange a real question and answer with another person.

**Architecture:** One Next.js web application calls Meta APIs on the server and persists memories, image versions, and messages in Supabase. Separate author and recipient capabilities protect draft and published views. Start with synchronous image routes after measuring real generation/edit latency; no background worker or realtime messaging.

**Tech Stack:** TypeScript, Next.js App Router, Tailwind CSS, Zod, OpenAI-compatible SDK for Meta, Supabase Postgres/Storage, Vitest, and one Playwright journey. Proposed hosting is Vercel Node/Fluid Compute, subject to Task 1.

**Spec:** [momentas design](../specs/2026-10-24-momentas-design.md).

**Status:** MVP implemented and deployed at https://momentas-hacktx.vercel.app. Source moved with user approval to /Users/rami/github/momenta. See ../../implementation-progress.md for verified task results, deviations and remaining submission work. The detailed checklist below preserves the original planning steps.

## Global Constraints

- There are approximately 16 working hours before judging.
- Meta is the primary track. Jester is optional if the finished experience naturally fits; Solana integration is outside this build.
- The user must be able to demonstrate the product alone.
- The first version has one storyteller sharing a memory with one recipient.
- The storyteller controls what the image expresses, including explicitly described feelings and perspective.
- Comparing two people's accounts of the same event is deferred.
- Typed text is required; voice is a stretch goal.
- Only explicitly published versions are visible to recipients. Human replies are never fabricated by a model.
- API/service keys and private draft data stay on the server. Shared URLs allow anyone possessing the link to view and leave a question; they do not prove a recipient's identity.
- One image style, one image per generation, one render in progress per memory, and a configurable global image-request ceiling starting at 24. Verify pricing before raising this ceiling.
- Preserve prior versions and written input on every provider, upload, or save failure. No automatic image retries.
- At hour 12, freeze scope. Reserve hours 14-16 for recording, submission, and buffer.

## Review Focus

1. A share token, guessed ID, or cross-origin request must not authorize draft reads, image generation, publishing, or a storyteller reply. Covered in Tasks 2, 4, and 5.
2. Sparse memories, invalid model JSON, and unsupported source quotes must not become asserted facts or bypass author review. Covered in Task 3.
3. Image timeout, malformed bytes, or upload failure must preserve the last successful image and allow an explicit retry. Covered in Task 4.
4. Double-clicks, repeated request IDs, stale completions, and concurrent image calls must not create duplicate paid attempts or exceed the configured cap. Covered in Task 4.
5. Editing after publication or receiving a question during republishing must not expose drafts or detach the question from the version actually viewed. Covered in Tasks 5 and 7.

## Shared interfaces

Define these in `src/lib/memory/types.ts` and validate incoming data in `schema.ts`:

```ts
type SourcedDetail = { text: string; sourceQuote: string };
type ScenePlan = {
  setting: SourcedDetail | null;
  people: SourcedDetail[];
  details: SourcedDetail[];
  perspective: SourcedDetail | null;
  feelings: SourcedDetail[];
  followUpQuestions: string[]; // maximum two, optional to answer
};
type ApprovedScene = {
  plan: ScenePlan;
  authorAdditions: string;
  confirmed: true;
};
type ImageVersion = {
  id: string;
  memoryId: string;
  parentVersionId: string | null;
  imagePath: string;
  scene: ApprovedScene;
  instruction: string | null;
  createdAt: string;
};
type MemoryMessage = {
  id: string;
  memoryId: string;
  versionId: string;
  role: 'recipient' | 'storyteller';
  displayName: string;
  text: string;
  parentId: string | null;
  createdAt: string;
};
type GeneratedImage = { bytes: Uint8Array; mimeType: string };
type RenderInput = {
  requestId: string; // UUID generated once per intentional user action
  scene: ApprovedScene;
  baseVersionId: string | null;
  instruction: string | null;
};
```

Additional draft and published view types may be chosen by the implementer. Public projections explicitly enumerate allowed fields; never spread a database row into a response. Include short-lived image URLs in view responses, never provider handles or base64 images.

**Interfaces:** `generateImage(scene: ApprovedScene): Promise<GeneratedImage>` and `editImage(image: GeneratedImage, scene: ApprovedScene, instruction: string): Promise<GeneratedImage>`. Use the one-off generation/edit endpoints documented in the spec. Configure the provider with zero automatic image retries and a 240-second timeout.

- [ ] Scaffold the smallest current stable Next.js/TypeScript app with server-only provider calls, a development server, lint/typecheck scripts, and Vitest. Pin installed versions in a lockfile.
- [ ] Supply credentials through local environment configuration. Confirm Spark/Image access and inspect current dashboard credit, pricing, and spending controls. Do not print keys or story contents into logs.
- [ ] Run `npx tsx scripts/check-meta.ts` against an explicitly fictional short memory, then edit its result with one meaningful spatial correction. Write generated files to a gitignored temporary directory. Log only latency, success/failure, dimensions, and available usage metadata. The script requires an explicit invocation and never runs as part of normal tests.
- [ ] Inspect both images: requested detail changes, important retained details are recognizable, and the style is acceptable. Confirm image bytes upload to private Storage and can be read through a temporary URL.
- [ ] Deploy a minimal server route on the candidate host and repeat a full generation/edit round through that route. Confirm its actual function deadline. Pass means a complete render plus upload/save fits the configured deadline; reserve 60 seconds of the 300-second route budget beyond the 240-second provider deadline.
- [ ] If latency exceeds that budget, choose a long-running Node host now and update the timeout consistently. If key access or generation does not work, resolve access before spending hours on UI. Record actual findings in README, with no fabricated latency promises.

### Task 2: Build the typed memory workspace and durable storage

**Files:** Create the migration, domain types/schema, `access.ts`, `supabase.ts`, `memories.ts`, memory create/read/update routes, root/author pages, and `tests/access.test.ts`.

**Interfaces:** `createMemory(input): Promise<{ id: string; authorToken: string }>`; `requireAuthor(memoryId: string, request: Request): Promise<void>`; `getAuthorMemory(memoryId: string): Promise<AuthorMemoryView>`; `saveDraft(memoryId: string, input: DraftInput): Promise<void>`. `DraftInput` contains title, authorName, recipientName, story, and optional scene plan. Define `AuthorMemoryView` alongside the other domain types before use.

- [ ] Write failing access tests: no/incorrect author token cannot read or update a draft; a share token cannot act as an author; tokens are stored as hashes; cross-origin mutations fail. Use realistic request/cookie fixtures, without live Meta calls.
- [ ] Add tables from the spec, server-only DB access, private Storage, and same-origin request validation. RLS denies anonymous direct table access; the service role stays server-only.
- [ ] Implement create, read, and draft-save endpoints. Issue a 32-byte author token in the memory-specific HttpOnly cookie and redirect to `/memory/[id]`. Check every access to an ID belongs to the authorized memory, including version and message references later.
- [ ] Build a simple form with title, names, story, optional perspective/feeling prompts, and explicit Save. Persist before beginning any model call. Apply the spec's exact text limits and preserve form input if saving fails.
- [ ] Run `npx vitest run tests/access.test.ts` and `npm run typecheck`. Expected: all tests and typecheck pass. Manually create, save, and refresh a memory; the draft remains and an incognito draft URL is denied.

### Task 3: Extract and review a scene without inventing the memory

**Files:** Create/update `schema.ts`, `prompts.ts`, `meta.ts`, the scene route, `memory-editor.tsx`, and `tests/scene.test.ts`.

**Interfaces:** `extractScene(story: string): Promise<ScenePlan>`; `validateSceneEvidence(story: string, plan: ScenePlan): void`; `buildImagePrompt(scene: ApprovedScene, instruction?: string): string`. Scene route returns a validated `ScenePlan`; the client never treats extraction as approval.

- [ ] Write failing tests for a sparse account with no emotion stated, unsupported source quotes, malformed provider output, and more than two follow-up questions. Use controlled provider responses. Assert unknown fields remain null/empty, invalid evidence is rejected, and no failed extraction overwrites a saved story or an earlier scene plan.
- [ ] Implement Spark structured extraction with exact source quotes for supplied facts and feelings. Validate quotes against the source text and validate the output schema on the server. Instructions request neutral optional follow-up questions and forbid invented identities, events, or inferred emotions. Human review remains essential; matching a source quote alone does not prove semantic accuracy.
- [ ] Implement a source-linked review form. Let the storyteller correct extracted details and add new details explicitly as their own additions. Include "This captures what I want to show" confirmation. A preview is not an approval; generating requires `confirmed: true` from the author action.
- [ ] Build the image prompt from the reviewed scene and author additions in the fixed photographic style, with subjective scale/mood drawn from supplied words and no embedded captions. Test that an edit includes the prior approved details plus the requested correction.
- [ ] Run `npx vitest run tests/scene.test.ts` and `npm run typecheck`. Expected: all checks pass. Manually confirm optional unanswered questions do not block approval and details can be corrected without another model call.

### Task 4: Generate, refine, and preserve image versions

**Files:** Create/update `render.ts`, `meta.ts`, `memories.ts`, the versions route, `image-review.tsx`, the migration, and `tests/render.test.ts`.

**Interfaces:** `renderVersion(memoryId: string, input: RenderInput): Promise<ImageVersion>`. The SQL reservation accepts memory ID/request ID, atomically checks the global ceiling and one active request, and returns a reservation or a typed conflict/budget error. An already completed request ID returns its original version rather than generating again.

- [ ] Write failing tests for provider timeout, unsupported image format, upload failure, concurrent duplicate request IDs, distinct simultaneous requests for one memory, exhausted global cap, and a stale completion after reservation expiry. Assert the previous version and draft survive, attempts are counted once, and only the valid reservation can attach its result.
- [ ] Implement the atomic reservation transaction, cap, request status, and expiry. Check permission and approved scene before reserving. Do not automatically retry an ambiguous provider failure. A retry is a new deliberate action with a new request ID.
- [ ] Implement initial generation and reference-image editing. Fetch prior image bytes from private Storage on the server; validate that the selected base version belongs to the memory. Pass approved scene plus correction to the edit adapter. Request base64 output to avoid dependence on temporary provider URLs.
- [ ] Upload successful bytes under a new version path, then create an immutable version row. If persistence fails, keep the old version and clear/expire the reservation safely; clean up an orphaned upload where possible. Do not change publication from this endpoint.
- [ ] Build version selection and a before/after review. Disable duplicate submission while generating, show honest loading stages and elapsed time, and offer explicit retry. Keeping an old version requires no new image call. Never display a prepared image as the result of a failed live request.
- [ ] Run `npx vitest run tests/render.test.ts` and `npm run typecheck`. Expected: all checks pass. Perform one real generate/edit through the app and inspect both images. Update the default prompt only if that inspection exposes a material problem.

- [ ] Add a publish action that validates selected-version ownership, copies approved caption to published state, and issues the separate share token. Republish reuses the existing link. Show the exact bearer-link visibility message from the spec before copying it.
- [ ] Build the recipient view with image, approved caption, author attribution, a question box, and fixed optional starters. Use no-store/noindex/no-referrer, and retrieve a fresh short-lived private-image URL on each page load.
- [ ] Implement recipient messages tied to the currently published version. If the publication changes between viewing and sending, return a conflict that preserves the typed message and asks the recipient to reload; do not silently attach it to the new version. Test this race explicitly.
- [ ] Implement author-authenticated replies to messages belonging to this memory. Derive the role/display identity server-side. Show earlier-version threads with a revision label after republishing, without disclosing other draft images. Refresh is sufficient; include a simple Refresh control.
